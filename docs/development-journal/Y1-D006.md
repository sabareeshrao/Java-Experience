# Engineering problem

Operations wants to run `survey-import` from a scheduled script. Day 5 could execute a valid import, but bad startup input did not have a stable process contract:

- `survey-import` with no record count could still reach a successful application ending.
- `survey-import abc` leaked a parsing failure rather than returning a controlled application exit status.

A scheduler needs a predictable process result, not just console text.

```text
valid survey import -> exit 0
missing required record count -> exit 2
invalid non-numeric record count -> exit 3
```

The top-level `main()` now recognizes `survey-import` explicitly. If its required record count is missing, it writes an error and invokes `System.exit(2)`. If parsing throws `NumberFormatException`, the application writes a controlled message and invokes `System.exit(3)`.

# System.exit() behavior learned today

`System.exit(status)` requests JVM termination with the supplied status. It is appropriate at a true process boundary such as a command-line/batch launcher when the caller needs a machine-readable success/failure status. It should not be scattered through domain code.

The call does not return normally. During JVM termination, registered shutdown hooks participate in the shutdown sequence. The resulting process status can then be read by the operating system, shell, scheduler, or CI tool.
